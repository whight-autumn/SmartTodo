# SmartTodo V1.4 Settings and Storage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a unified SmartTodo settings center for Windows startup, AI credentials, and verified whole-directory runtime-data migration, then update the application to V1.4.0 for user review without packaging or pushing.

**Architecture:** A new main-process runtime-data manager owns the stable bootstrap file, path validation, manifest verification, and pre-`userData` migration. A separate settings IPC module owns Windows login startup and capability-scoped renderer bridges. The existing settings dialog becomes a three-module settings center whose controller is extracted from the large renderer entry point and continues to use the current visual system and AI storage keys.

**Tech Stack:** Electron 31, CommonJS JavaScript, HTML/CSS, GSAP 3, Node `fs`/`path`/`crypto`, `node:test`, Electron UI smoke/layout tests.

**Spec:** `docs/superpowers/specs/2026-10-13-v1.4-settings-storage-design.md`

## Global Constraints

- Target version is exactly `1.4.0`; preserve all V1.0.7–V1.3.1 data and existing `localStorage` keys.
- Default runtime path remains `%APPDATA%\SmartTodo\运行数据`; custom destinations are the exact selected directory.
- Keep `contextIsolation: true` and `nodeIntegration: false`; expose no generic filesystem, arbitrary IPC, or renderer-authored path API.
- Migration must run before Chromium opens `userData`, copy every ordinary file, reject links/path escapes, and verify relative path, byte size, and SHA-256 before switching.
- Migration failure must boot from the old directory without overwriting the target or deleting user data; successful migration retains a timestamped source backup.
- Auto-start is Windows-only and launches with `--hidden` so the main window does not steal focus.
- Preserve the established warm-paper/dark-lacquer, ink, restrained jade, Noto Serif SC heading, fine-line, 6–14px radius design system.
- Support keyboard navigation, screen readers, reduced motion, light/dark themes, 1366×768 through 2560×1440, narrow windows, and Windows 100%/125%/150% scaling.
- Do not package, push GitHub, or create a GitHub Release until the user reviews and explicitly approves the completed source, screenshots, tests, and documentation.

## Review Focus

- A destination that changes between selection and restart must be rejected without touching the old directory; Task 1 pins revalidation immediately before commit.
- A source containing a symbolic link or a file that changes during hashing must fail closed and boot from the old path; Task 1 tests both cases.
- A renderer must not fabricate a path by replaying or stealing another window's selection token; Task 3 binds one-use tokens to `webContents.id` and tests replay/cross-sender rejection.
- Windows may report a different login-startup state after a setter call; Task 2 tests that the returned state comes from `getLoginItemSettings`, not optimistic UI state.
- Long Chinese paths and a 1366×768 viewport must not hide migration warnings or actions; Tasks 4 and 6 add layout and keyboard checks for that exact condition.
